# BantayBaha Cainta — System blueprint

## Goal and boundaries

A web-only school prototype for a Cainta DRRMO flood-reporting workflow. Residents submit reports and follow their own status updates. Authorized staff review reports and manually update status.

No sensors, kiosks, QR devices, automatic flood detection, or automatic rescue dispatch. The prototype is not an official emergency service. Use sample data until operational and privacy arrangements have been reviewed.

## Current workflow

Resident registration/login → submit report → Firestore validation and storage → staff review/status update → resident sees their own updated report.

Firebase Authentication identifies the account. Its UID becomes the `residentId` on new reports. The frontend queries only that resident's documents; Firestore rules independently enforce the same ownership boundary. An active staff account can query all reports.

Switching accounts unsubscribes old listeners and hides reports from the previous account. Loading and errors are shown separately from an empty report list.

## Roles and permissions

| Role | Current access |
| --- | --- |
| Visitor | Homepage and public preparedness guide; login required for reporting and My Reports. No database report access. |
| Resident | Register/login, submit own report, read own reports and status. Cannot update or delete reports. |
| Active staff | Read all reports, filter by status, view summary counts, update status. Cannot rewrite resident content or delete reports. |
| Project administrator | Manages Authentication users and staff membership through the Firebase console; no administrator management page yet. |

Staff membership is a `staff/{uid}` document with boolean `active: true`, not an email check or a role selected during registration. Signed-in accounts may read their own membership document. No browser account may list, create, update, or delete staff membership documents. Removing membership or setting `active: false` prevents subsequent staff-authorized requests; it cannot erase data already seen by a previously authorized person.

## Current data model

Firebase Authentication stores account identities; this milestone does not create a separate `users` collection.

### `floodReports/{reportId}`

| Field | Storage and validation |
| --- | --- |
| `residentId` | Firebase Authentication UID; must equal the submitting account. |
| `barangay` | Nonblank string, maximum 100 characters. |
| `locationDetails` | Nonblank string, maximum 300 characters. |
| `severity` | `Low`, `Medium`, or `High`; resident-reported, not sensor-verified. |
| `description` | Nonblank string, maximum 3,000 characters. |
| `photoName` | Filename only, maximum 255 characters; empty string when absent. |
| `status` | Initially `Submitted`; only staff can change it. |
| `createdAt` | Server-generated Firestore Timestamp on creation. |
| `updatedAt` | Server-generated Firestore Timestamp on creation/status update. |

The document ID is generated by Firestore. New documents must contain exactly the allowed fields; rules reject extra fields. Residents cannot forge owner IDs, starting status, or timestamps. Report deletion is denied to all browser clients.

For compatibility, the display layer also accepts older ISO-string dates. Pre-account demo reports retain their original browser IDs and are visible to staff, not automatically reassigned to residents. No legacy data was deleted as part of the account update.

### `staff/{uid}`

```json
{
  "active": true
}
```

The document ID must be the staff account's actual Firebase Authentication UID. Passwords never belong in this collection. This collection is not a public staff directory.

## Status meanings

- **Submitted:** received by the database; awaiting staff review.
- **Under Review:** staff are checking the information.
- **Verified:** staff have confirmed available details.
- **Resolved:** staff have marked the reported concern as addressed.
- **Closed:** staff have closed the report.

All statuses are manually selected by authorized staff. The current rules permit a staff member to select any valid status; they do not enforce a one-way transition sequence. A status change does not automatically dispatch personnel or guarantee a response time.

## Implemented versus planned

Implemented: homepage, account registration/login/logout, reporting form, account-owned My Reports, staff dashboard, status filter/counts, database validation, automated emulator tests, and a public preparedness guide with source links and a temporary 7-item go-bag checklist.

Preparedness uses static content (`src/data/preparedness.ts`) and scoped styling (`src/pages/Preparedness.css`). It renders before the authentication loading/error guard, so a failed account check does not block the guide. Checklist state is in memory only and resets on page exit or refresh. No new database collection, upload, or staff editing interface is involved. Guidance is a manually maintained summary, not a live advisory or DRRMO-approved publication.

Planned, not yet working features:

- Advisory and emergency contact pages with reviewed content; DRRMO review of the existing preparedness summary before official use.
- Actual optional image upload with appropriate access controls; the current control records only a filename.
- Additional filters by severity, date, and barangay.
- Internal staff notes. Store these in a separately protected location, not in resident-readable report documents.
- Staff account-management interface, password recovery, and email verification.
- Public deployment, abuse controls, retention decisions, and operational review.

Email/password registration does not verify that the person lives in Cainta. Frontend password guidance is not a substitute for configuring any required Firebase password policy.

## Testing

`tests/firestore.test.mjs` has 16 tests using only local Firebase emulators. Tests include unauthorized reads/writes, resident isolation, spoofed ownership, extra/invalid fields, timestamps, staff-only updates, membership revocation, legacy compatibility, status listeners, and registration/login/logout.

See the root README for commands and the browser demonstration checklist. The local test website uses port 5174 and project `demo-bantaybaha`; the regular Vite website normally uses port 5173 and the configured real Firebase project.
